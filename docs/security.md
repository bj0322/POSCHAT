

## 업데이트 신뢰 모델
- 앱은 `updates.UPDATE_BASE_URL`(업데이트 서버)에서 새 버전을 확인합니다. 서버는 GitHub 릴리스를 10분마다 복사할 뿐 서명 키를 갖고 있지 않아서, 서버가 침해되거나 연결이 변조돼도 서명을 위조할 수 없습니다. 막지 못하는 것: 낡은(서명된) 릴리스를 계속 보여 줘서 업데이트를 막는 일, 도청.
- 서명은 릴리스 CI(`publish` 작업)가 `UPDATE_SIGNING_KEY` 시크릿으로 만듭니다(`tools/update_sign.py sign`). 앱에 들어 있는 공개키(`updates.UPDATE_PUBLIC_KEYS`)와 맞지 않으면 릴리스가 만들어지지 않습니다.
- **키 교체**: ① `python tools/update_sign.py keygen | gh secret set UPDATE_SIGNING_KEY`로 개인키를 시크릿에 바로 넣고(파일에 남기지 않음) 새 공개키만 봅니다. ② 새 공개키를 `UPDATE_PUBLIC_KEYS`에 **옛 키와 함께**(`("옛", "새")`) 넣고, 옛 키로 서명한 마지막 릴리스를 한 번 냅니다(앱이 새 키를 받아 둠). ③ 모든 사용자가 그 버전으로 넘어간 뒤 옛 키를 뺍니다. 시크릿을 새 키로 바꾸는 시점은 ②의 릴리스가 끝난 뒤입니다.
- 개인키가 새어 나갔다면 공격자는 옛 키를 가진 모든 앱에 설치 파일을 줄 수 있습니다. 서버의 릴리스를 지우고(서버는 GitHub 릴리스를 복사하므로 GitHub 릴리스도 지움) 새 공개키가 든 설치 파일을 사용자가 직접 설치하게 안내해야 합니다.
- 개인키를 잃으면 새 키로 서명한 릴리스를 기존 앱이 받아들이지 않습니다. 이때도 새 공개키가 든 설치 파일을 직접 설치해야 합니다.
- 1.18.3부터 서버는 `https://pidstech.com`입니다(서명 확인은 그대로). 1.18.2 앱은 옛 주소 `http://3.38.118.65`를 쓰므로, 서버는 그 주소도 서명된 같은 파일로 계속 서비스합니다.
