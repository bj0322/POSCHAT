# POSTECH SSO·PLMS 연계 검토

검토일: 2026-10-26. 범위는 Windows·macOS POSCHAT이다. 공개 로그인 화면, 비인증 REST 응답, 현재 코드를 확인했다. 실제 계정 로그인·로그인 후 강좌 조회는 수행하지 않았다.

## 판단

**연결 가능성이 높다. 먼저 기존 브라우저에서 사용자가 SSO·2차 인증을 직접 마친 뒤 필요한 PLMS 페이지를 읽는 방식으로 확인하는 것이 가장 작다.** 상시 자동 동기화와 POSCHAT 자체의 학교 계정 로그인은 별도 요구이며 현재 검증되지 않았다.

| 연결 수준 | 판단 | 남은 확인 |
|---|---|---|
| POSCHAT 안에서 PLMS 열기·SSO 로그인 | 기존 브라우저 구조로 시도 가능 | 실제 Windows·macOS에서 리다이렉트·쿠키·2차 인증 왕복 |
| 로그인 후 공지·과제 페이지 읽기·요약 | 기존 페이지 읽기·첨부 기능 활용 가능 | 실제 로그인 후 DOM·iframe·권한별 화면 |
| 수강 과목·과제·마감일 자동 동기화 | API 권한 확보 시 우선 검토 | 토큰 발급 방식·허용 함수·버전·호출 제한 |
| POSCHAT 자체를 POSTECH SSO 서비스로 등록 | 공개 자료만으로 가능 여부 확정 못함 | 학교 담당자의 서비스 등록·인증 규격·콜백 허용 |

## 공개 근거와 직접 확인

- [PLMS 로그인 화면](https://plms.postech.ac.kr/login/index.php)에 SSO Login이 있으며 실제 링크는 [PLMS 서비스 로그인 진입점](https://plms.postech.ac.kr/passni/sso/spLogin.php)이다. 세션마다 달라지는 인증 요청 값을 하드코딩하지 않고 이 진입 흐름을 따른다.
- [교육혁신센터 PLMS 안내](https://ice.postech.ac.kr/index.php?hCode=PROF_01_10)는 통합로그인과 PLMS 직접 접속을 안내한다.
- [POSTECH 2차인증 안내](https://sso.postech.ac.kr/sso/usr/postech/self/stonePassInfo)는 교외 접속 시 2차 인증과 StonePASS 사용을 설명한다. 로그인과 2차 인증은 사용자가 직접 진행하는 방식이 적합하다.
- 2026-10-26 비인증 GET으로 `https://plms.postech.ac.kr/webservice/rest/server.php`를 한 번 확인했다. HTTP 200, XML `moodle_exception`, `invalidtoken`, “잘못된 토큰 - 토큰이 발견되지 않았습니다.”를 반환했다. **REST 처리 경로가 응답한다는 근거이며, 학생의 토큰 발급 가능성이나 특정 함수 허용을 증명하지 않는다.**
- [Moodle 공식 External Services 문서](https://moodledev.io/docs/apis/subsystems/external/)는 외부 API와 사이트별 API 문서를 설명한다. 이는 Moodle의 일반 기능이다. PLMS의 실제 버전·활성화 함수와 동일하다고 가정하지 않는다.
- [Moodle 웹서비스 클라이언트 문서](https://docs.moodle.org/dev/Creating_a_web_service_client)는 REST 요청의 `wstoken`·`wsfunction`을 설명한다. 이 페이지는 구형 문서이므로 실제 PLMS 설정 확인이 우선이다. **브라우저 SSO 세션과 웹서비스 토큰을 같은 인증 수단으로 취급하지 않는다.**

## 현재 POSCHAT에서 재사용할 부분

- `browser_api.py`: `browser_open`, `browser_attach`, `browser_external`. PLMS 주소를 열고 사용자가 선택한 내용을 첨부하는 기능이 이미 있다.
- `browser.py`: 외부 웹페이지를 앱의 Python API에서 격리하고 페이지 글을 읽는다. `profile_dir()`는 브라우저용 저장소 경로를 제공하며 Windows 백엔드가 사용한다. 운영체제 기본 브라우저의 기존 로그인 세션이 이 뷰와 공유된다고 가정하지 않는다.
- `browser_agent.py`: 비밀번호·OTP 입력을 민감 동작으로 취급한다. 자동 로그인 코드를 새로 만드는 것보다 사용자 직접 로그인이 간단하다.
- `connectors.py`, `secret_store.py`: API 방식으로 확정되면 기존 연결 설정·비밀 저장 구조를 재사용할 수 있다. 현재 PLMS 전용 커넥터는 없다.
- 기존 브라우저는 다운로드를 막는다. 페이지 글 읽기와 강의자료 파일 내려받기는 다른 기능이다. 강의자료 연결은 인증된 다운로드 경로를 별도로 검토해야 한다.
- 현재 브라우저는 동시 실행 채팅 중 한 세션만 에이전트가 사용한다. 여러 PLMS 동기화 작업이 독립 브라우저를 쓰는 구조는 아니다.

그래프 검색으로 관련 파일 위치를 찾은 뒤 실제 소스로 위 내용을 확인했다. 기존 그래프는 최신 코드 전체를 보장하지 않으며 재생성하지 않았다.

## 권장 구현 순서

1. **로그인·읽기 시범**: 기존 브라우저에서 PLMS 로그인 페이지 열기 → 사용자 SSO·StonePASS 인증 → 과목 페이지 열기 → 선택한 공지 또는 과제 내용을 첨부·요약. 처음에는 전용 OAuth 서버나 새 브라우저 엔진을 추가할 필요가 없다.
2. **실제 화면 확인**: Windows·macOS 각각에서 로그인 왕복, 재시작 후 세션 상태, 만료·로그아웃, 페이지 읽기를 확인한다. iframe·팝업 때문에 막히면 해당 동작만 보완한다. 외부 브라우저로 로그인해도 내장 브라우저까지 로그인된다고 판단하지 않는다.
3. **자동 동기화 판단**: 교육혁신센터에 외부 앱 웹서비스 사용 가능 여부·사용자 토큰 발급·허용 함수·요청 한도를 확인한다. 문의 초안 항목만 기록했으며 실제 연락은 하지 않았다.
4. 토큰이 허용되면 수강 목록·공지·과제·마감일의 **조회 기능**부터 기존 커넥터에 추가한다. 후보 함수는 Moodle의 `core_webservice_get_site_info`, `core_enrol_get_users_courses`, `mod_assign_get_assignments`, `core_calendar_get_calendar_events`이며 PLMS에서의 활성화 여부는 미확인이다.
5. API를 사용할 수 없다면 로그인된 화면에서 사용자가 요청할 때 읽는 방식으로 범위를 정한다. HTML 변경에 의존하는 백그라운드 수집을 먼저 만들지는 않는다.

로그인 정보·OTP·쿠키·API 토큰은 대화나 모델 입력으로 넘기지 않는다. PLMS 페이지는 기존 `wrap_untrusted` 방식의 외부 데이터로 처리한다. 연결 해제 시 무엇을 지우는지는 브라우저 세션과 API 토큰을 구분해 설계한다.

## 완료 조건과 미확인 사항

- 본인 계정의 과목·공지·과제 마감일을 실제 앱에서 읽고 원문 링크로 검증할 수 있어야 한다.
- 세션 만료 시 재로그인을 안내하고 계정 전환 시 이전 계정 데이터를 섞지 않아야 한다.
- 사용자 계정·네이티브 앱으로 인증 성공 여부를 확인하기 전에는 “SSO 연동 완료”로 표시하지 않는다.
- 강의자료 다운로드, 성적, 제출·출석·퀴즈, 상시 동기화, 학교가 승인한 SSO 서비스 등록은 이번 검토만으로 지원을 약속하지 않는다.

후속 구현: v1.18.4에 로그인된 브라우저 쿠키를 로컬에서 재사용하는 조회 기능과 에이전트 도구를 추가했다. [사용법·검증 범위](plms-guide.md)를 참고한다. 실제 학교 계정 인증과 학교 SSO 서비스 등록은 수행하지 않았다.
